1. Amendments to Tier A

Writing the implementation found three places where the specification as drafted is either impossible to implement exactly in JavaScript or expensive for no benefit. Tier A is the one tier that can never change after ship, so these are proposed now.

Amendment 1 — replace PCG32 with xoshiro128**

PCG32 has 64-bit state and a 64-bit multiply. JavaScript has neither natively. Implementing it means BigInt (roughly 50x slower, and it allocates — unacceptable in a per-frame path) or hand-rolled 64-bit multiplication in 32-bit halves, which is a correctness hazard in the single most determinism-critical function in the machine.

xoshiro128** uses four 32-bit words and nothing but 32-bit operations. Statistically equivalent for game use, several times faster, and it needs no tricks. Best of all it is free: the state is 4 x u32 = 16 bytes, exactly the size already reserved at 0x2100. No memory-map change.

function rotl(x, k) { return ((x << k) | (x >>> (32 - k))) >>> 0; }

function next(s) {                         // s: Uint32Array(4)
  const r = Math.imul(rotl(Math.imul(s[1], 5) >>> 0, 7), 9) >>> 0;
  const t = (s[1] << 9) >>> 0;
  s[2] ^= s[0]; s[3] ^= s[1]; s[1] ^= s[2]; s[0] ^= s[3]; s[2] ^= t;
  s[3] = rotl(s[3], 11);
  return r;                                // u32
}
Amendment 2 — rounding is floor, not truncation toward zero

The draft says fixed-point multiply and divide truncate toward zero. Every fast fixed-point implementation uses an arithmetic shift right, which is floor. They differ for negative results, and truncate-toward-zero costs a sign test and a correction on every multiply in the machine.

Specify floor. It is what the hardware does, what the exact algorithm in section 5 naturally produces, and it is consistent: floor has no discontinuity at zero, so a sprite drifting left across the origin moves smoothly rather than pausing for one sub-pixel.

Amendment 3 — bound the domain of rnd(n)

The draft defines rnd(n) = (u64(rand32()) * u64(n)) >> 32. In JavaScript that product reaches 263, far past the 253 where doubles are still exact integers — so the naive transcription is silently wrong for large n, and wrong differently on different engines.

Bound n to [1, 2^31) and specify the split algorithm in section 5.3, whose every intermediate stays below 248. Out-of-range n is a build-time error, not a runtime surprise.

Everything else in Tier A survived implementation review unchanged.

2. Repository and packages

A pnpm workspace. TypeScript throughout, compiled to ES2022. Zero runtime dependencies in every package that ships to a player — the runtime must stay under 100 KB gzipped and must never inherit somebody else's determinism bug.

3. Thread topology

  +----------------------------- host page ------------------------------+
  |                                                                      |
  |  <iframe src="https://cart.sq1.run/player"                           |
  |          sandbox="allow-scripts">      no allow-same-origin          |
  |    +--------------------- MAIN THREAD ---------------------+         |
  |    |  shell (bezel, touch pad, pause)                      |         |
  |    |  input capture -> 4 bytes                             |         |
  |    |  rAF + accumulator  owns the clock                    |         |
  |    |  canvas: putImageData / texSubImage2D                 |         |
  |    |  AudioContext + AudioWorkletNode                      |         |
  |    +---------------^---------------------------|----------+         |
  |                    | FRAME {rgba, audio}       | STEP {frame, input} |
  |    +---------------|---------------------------v----------+         |
  |    |                      WORKER                           |         |
  |    |  64 KB ArrayBuffer  = the entire machine              |         |
  |    |  scrubbed realm + cart closure                        |         |
  |    |  rasterizer (writes packed nibbles into RAM)          |         |
  |    |  palette expand -> RGBA out buffer (transferred)      |         |
  |    +-------------------------------------------------------+         |
  +----------------------------------------------------------------------+
Decision — the rasterizer lives with the cart, in the worker

A cart makes hundreds of draw calls per frame. If the rasterizer sat on the main thread, every gfx.spr would be a postMessage and the design would be dead on arrival. The worker owns the 64 KB and draws into it directly; only the finished frame crosses the boundary.

Decision — transferables, not SharedArrayBuffer

SharedArrayBuffer requires cross-origin isolation (COOP + COEP), which is awkward to combine with a sandboxed iframe holding an opaque origin, and fails silently in configurations you will not notice until a user reports it.

Instead, ping-pong two 64 KB RGBA buffers as transferables. Transfer is a pointer move, not a copy. Sixty transfers per second of a 64 KB buffer is free. Revisit SAB only if profiling ever says to.

Decision — the main thread owns the clock

The worker must never decide when to step, because worker scheduling is at the mercy of the browser and the simulation rate is normative. Main runs rAF, accumulates real time, and emits exactly one STEP per 1/60 s of simulated time, clamped to five per presented frame. The worker is a pure function of the messages it receives — which is also what makes the headless prover in cli able to reuse it unchanged.

3.1 Frame timeline

  rAF(t)
    dt = min(t - last, 100ms)            clamp: backgrounded tab
    acc += dt
    steps = 0
    while (acc >= 16.667 && steps < 5) {
      post STEP{frame++, input}          input sampled ONCE, before the step
      acc -= 16.667; steps++
    }
    present(latestFrameBuffer)           may be one frame behind; documented

Display latency is one frame by construction. Input latency is not affected, because input is sampled on the main thread at the moment the STEP is posted.

4. Host–worker protocol

Six message types. Everything is structured-cloneable; the two buffers are transferred.

// main -> worker
type ToWorker =
  | { t: 'load';     cart: ArrayBuffer; seed: number }
  | { t: 'step';     frame: number; input: Uint8Array /* 4 */; out: ArrayBuffer }
  | { t: 'snapshot' }
  | { t: 'restore';  ram: ArrayBuffer }

// worker -> main
type FromWorker =
  | { t: 'ready';    abiMinor: number; title: string }
  | { t: 'frame';    frame: number; out: ArrayBuffer;
                     audio: Int32Array; tookMs: number }
  | { t: 'snapshot'; ram: ArrayBuffer }
  | { t: 'fault';    phase: 'load'|'boot'|'tick'; frame?: number; message: string }
Gotcha — a transferred buffer is gone

After postMessage(msg, [out]) the sender's view is detached and every read returns zero. Keep exactly two buffers and treat them as a strict alternation: main sends A and holds B; the worker returns A; main presents A and sends B. A dropped or duplicated message desynchronizes the pair, so assert on frame parity in development builds.

4.1 Faults

A cart that throws produces a fault, not a dead tab. The player shows the phase, the frame index, and the message, and offers to rewind to the last snapshot. A tick that exceeds the watchdog produces a fault with message: 'deadline' after the worker is terminated and a fresh one is spun up from the last snapshot.

5. Exact arithmetic

This is the most correctness-critical code in the project. If it is wrong, every replay in the archive is wrong, and the failure appears thousands of frames after the mistake.

5.1 Fixed-point multiply

The naive (a * b) >> 16 is wrong in JavaScript, and it is worth being precise about why, because the obvious explanation is not the real one. Split the operands into 16-bit halves so no intermediate exceeds 247.

const MIN = -2147483648, MAX = 2147483647;
const sat = (r) => r < MIN ? MIN : r > MAX ? MAX : r | 0;

// a, b are i32 holding 16.16.  Result is floor((a*b) / 65536), saturated.
export function fmul(a, b) {
  const ah = a >> 16, al = a & 0xffff;    // ah signed, al unsigned
  const bh = b >> 16, bl = b & 0xffff;
  const hi  = ah * bh;                    // <= 2^30
  const mid = ah * bl + al * bh;          // <= 2^47
  const lo  = (al * bl) >>> 16;           // <  2^16, exact floor
  return sat(hi * 65536 + mid + lo);      // <  2^48, exact in a double
}

export function fdiv(a, b) {
  if (b === 0) return a >= 0 ? MAX : MIN; // defined, never a trap
  return sat(Math.floor((a * 65536) / b));// a*65536 <= 2^47, exact
}
Gotcha — the real defect is >>, not float precision

The tempting explanation is that a*b reaches 262, past the 253 where doubles stop being exact integers. That is true and it is not what breaks the naive form. The killer is >>, which applies ToInt32 and wraps the product modulo 232. It fails instantly, on small ordinary inputs, long before precision is in play.

The float argument is subtler than it looks, and it turns out not to bite: Math.floor((a*b)/65536) with saturation actually agrees with the exact result everywhere. Inexactness needs |a*b| > 2^53, which forces the quotient past 237 — far beyond FP_MAX, so it saturates to the same endpoint whatever the rounding did. And any result that does not saturate needs |a*b| <= 2^47, which is exact. The two regions cannot overlap; there is a comfortable gap between 247 and 253. Verified over 3 x 106 random i32 pairs, 2.96 x 106 of them with inexact products: zero mismatches.

Keep the split multiply anyway. It is exact by construction rather than by a saturation argument that has to be re-derived by every reader, and it ports unchanged to C, Rust and WASM, where the saturation step is not free and the reasoning above does not carry.

Gotcha — why the split form is exact

a*b = ah·bh·2^32 + (ah·bl + al·bh)·2^16 + al·bl. Dividing by 216, the first two terms stay integral and only al·bl contributes a fraction — and al, bl are non-negative so >>> 16 is exactly floor. Every intermediate is below 248, well inside the exact-integer range.

Do not trust that argument — test it. A property test over 106 random pairs against a BigInt reference is thirty lines and it is the highest-value test in the repository. Mutation-test the test, too: break the implementation on purpose and confirm the suite goes red. Dropping the lo term, substituting Math.trunc for floor, and reinstating >> 16 were each caught within ten iterations.

5.2 Trigonometry is a committed table

sys.sin and sys.cos take an angle in 1024 steps per turn and read a 1024-entry Int32Array of 16.16 values. That table is generated once, committed to conformance/fixtures/sin1024.bin, and is normative.

Decision — ship the table, not the formula

A formula invites every implementation to compute it with its own libm, which is precisely the last-unit-in-the-last-place divergence the specification deletes Math to avoid. A committed binary blob cannot diverge. It is 4 KB, it loads instantly, and conformance testing it is a byte comparison.

5.3 Bounded random

// n in [1, 2^31).  Unbiased, no division by a runtime value, all exact.
export function rnd(s, n) {
  const r   = next(s);                    // u32
  const hi  = (r >>> 16) * n;              // < 2^47
  const lo  = (r & 0xffff) * n;            // < 2^47
  const q   = Math.floor(hi / 65536);
  const rem = hi - q * 65536;             // < 65536
  return q + Math.floor((rem * 65536 + lo) / 4294967296);
}

rndf() is simply next(s) >>> 16 — a 16.16 value in [0.0, 1.0).

6. The rasterizer

The framebuffer stays packed at 4 bits per pixel, exactly as the memory map says, because sys.peek must see the real bytes. An unpacked shadow buffer would be faster per pixel and would make the machine a lie.

6.1 Pixel write

const STRIDE = 64;                        // 128 px / 2 px per byte

function pset(fb, x, y, c) {              // caller has already clipped
  const i = (y << 6) + (x >> 1);
  const b = fb[i];
  fb[i] = (x & 1) ? ((b & 0x0f) | (c << 4))
                  : ((b & 0xf0) | c);     // even x = low nibble = left pixel
}
Gotcha — clip once, at the edge

Clipping inside pset puts a branch on the hottest path in the machine. Clip in each primitive — intersect the shape with the clip rectangle before the loop — and let pset assume validity. Then assert validity in development builds only, compiled out of release.

6.2 Sprite blit, with the fast path

Source sprite data is also 4 bpp. When source and destination x are both even and no per-pixel transparency test is pending, whole bytes copy two pixels at a time. Otherwise fall back to nibble shifting.

if (((sx | dx) & 1) === 0 && !transparent && !flipX) {
  // byte-aligned: copy w/2 bytes per row
} else {
  // per-pixel: read nibble, test transparency, remap, write nibble
}

The fast path handles the common case — tile maps drawn on an 8-pixel grid — which is most of the pixels most games push.

6.3 Palette expand, once per frame

// rebuilt only when PALETTE_LIVE or PALETTE_HW is dirty
lut32[i] = (255 << 24) | (bColor << 16) | (gColor << 8) | rColor;

// 8192 bytes in, 16384 pixels out, one pass, zero branches
let o = 0;
for (let i = 0; i < 8192; i++) {
  const b = fb[i];
  out32[o++] = lut32[b & 0x0f];
  out32[o++] = lut32[b >>> 4];
}
Gotcha — the LUT is little-endian

Writing RGBA through a Uint32Array assumes little-endian byte order. That holds on every platform this will realistically run on, but assuming it silently is how a port breaks. Detect once at startup with a two-byte probe and select the other packing order if it fails — four lines, and it turns a mystery into a branch taken never.

6.4 Presenting

Main thread wraps the transferred buffer in a Uint8ClampedArray, builds an ImageData, and either putImageData onto a 128 x 128 backing canvas which is then drawn scaled with imageSmoothingEnabled = false, or uploads it with texSubImage2D if a CRT shader is active. CSS carries image-rendering: pixelated and the scale is snapped to an integer.

7. Audio

An AudioWorkletProcessor renders four channels in 128-sample quanta. It receives commands, never timing.

  worker (sim)          main            audio worklet thread
      |                   |                      |
      |  audio: Int32Array|                      |
      |------------------>|  port.postMessage    |
      |                   |--------------------->| enqueue
      |                   |                      | render 128 frames
      |                   |                      | at its own clock
Gotcha — never read the audio clock

An AudioContext runs on its own hardware clock, which drifts against rAF and differs per device. Deriving anything in the simulation from currentTime makes the game nondeterministic and, worse, makes it nondeterministic only on some hardware. The street is one way: the sim emits commands, the mixer consumes them, nothing flows back. This is also why the specification leaves audio non-normative — mixing quality can differ without a replay diverging.

Waveforms are pulse with duty, triangle, sawtooth, noise (a 15-bit LFSR, seeded per channel and part of no snapshot because it feeds nothing back), and a 32-step user wavetable. Per-channel envelope is attack/decay/sustain/release in frame units.

8. The sandbox

8.1 Three layers, and only two are portable

Treating the sandbox as one thing is the mistake that produces a sandbox which looks hardened in tests and is not.

LayerWhat it doesWhere it can run
0 Source rejectionRefuses import and export at token levelAnywhere — build time and load time
1 Parameter shadowingEvery dangerous global is a parameter, passed undefinedAnywhere, always on
2 Realm hardeningDeletes globals, neuters the four code constructors, freezes intrinsicsWorker only

Layer 2 cannot run in-process: deleting Math or neutering Function.prototype.constructor in a test runner's own realm breaks the runner. It belongs in the worker, where the realm hosts exactly one cart.

Gotcha — Layer 0 exists because import() is syntax, not a name

import("node:fs") inside a new Function body resolves. It is not an identifier, so no parameter can shadow it and no delete can remove it. The only place to stop it is before compilation, by refusing the token.

The bootstrap, and why it is nested

const F = Function;                       // capture BEFORE anything is scrubbed

// A sloppy OUTER function holds the parameters; the cart lives in a strict
// INNER one. `new F("eval", '"use strict"; ...')` is a SyntaxError in every
// engine -- strict code may not BIND the name `eval` -- so the shadow list
// and the strict cart body cannot share one scope.
const factory = new F(...SHADOW, 'gfx','snd','inp','sys', `
  return (function () {
    "use strict";
    ${source}
    return { boot: typeof boot === "function" ? boot : undefined,
             tick: typeof tick === "function" ? tick : undefined };
  })();
`);
Gotcha — the nesting opens a hole, so close it first

A source beginning }, evil(), function () { closes the inner function and continues in the sloppy outer scope, where a plain call's this is the real global. Layer 2 does not save you: it hands over the hardened global, which still holds console and postMessage by design.

Close it by compiling every source on its own as a strict function body first. A complete FunctionBody has balanced braces and cannot close one it did not open.

Gotcha — after the delete pass, name nothing you deleted

This one shipped, passed every test, and did nothing. The delete pass removes the global Function; the neutering step then referred to Function by identifier while building its target list, outside any try. scrubRealm threw ReferenceError: Function is not defined on the first line of real work — so no constructor was neutered, no intrinsic frozen, and every escape stayed open.

Nothing in-process could see it, because a test runner's realm still has Function. It took spawning a real worker and running the real scrub on its real global to find. The rule: after the delete pass, no code in the scrub may name a scrubbed global by identifier — hold module-load references instead.

Gotcha — delete globalThis.fetch deletes nothing in a browser

The same class of bug, found the same way, one realm further out. On a Node worker global every scrubbable name is an own property, so delete works. On a web global it does not: WebIDL puts interface operations and attributes on the interface prototype — DedicatedWorkerGlobalScope.prototype, WorkerGlobalScope.prototype, EventTarget.prototype — and only interface objects on the global itself.

So delete globalThis.fetch removes nothing, returns true, and leaves fetch one hop up the chain. Measured on Chromium 153 and Firefox 155: 18 of 45 names survived a scrub that reported success — the network, importScripts, indexedDB, caches, crypto, navigator, location, the timers, and the event-listener surface.

The fix is to walk the prototype chain and delete the own property wherever it actually lives, stopping at Object.prototype. Node's report is byte-identical afterwards, because the walk finds everything on the first object.

The pattern behind both — and the only thing that found either

Twice now, Layer 2 has silently done nothing while a green suite said otherwise. Different mistakes, one shape: a component that can only run in an environment the tests do not create is not being tested — a stand-in that shares its name is.

Neither bug was findable by reading the code, and neither was findable in-process. Both took building the real environment: a real worker, a real global, the real function. Budget for that explicitly, and run it on every realm you ship to — the browser defect was invisible on Node, and the Node defect was invisible everywhere else.

A corollary worth keeping: a security check that reports success is not evidence it did anything. Have the scrub return what it actually deleted, froze and neutered, and assert on that report rather than on the absence of a thrown error. Both defects announced themselves the moment the report was read instead of trusted.

Gotcha — scrubbing is defense in depth, not a proof

Realm scrubbing has a long tail: the four code constructors, prototype walks that start from an ABI method, getters on inherited prototypes, and whatever the next engine ships. Close the ones you know and expect to miss some. Layer 1 alone is not a security boundary — write that where implementers will read it, not only where auditors will.

The actual boundary is elsewhere. Separate origin, sandbox="allow-scripts" without allow-same-origin, CSP with connect-src 'none', and a worker you can terminate. A cart that defeats every line above still lands somewhere with no network and no cookies. Build the scrub for determinism first and containment second, and let the origin do the security.

8.2 The canary suite

Maintain a directory of escape attempts as ordinary test carts — reaching a global, constructing a function, touching the network, reading the clock, mutating a frozen intrinsic. Each asserts that the attempt throws or yields undefined. Every new engine release is a reason to run it. This suite only ever grows.

9. Container codec

9.1 Decoding is adversarial input

A cart arrives from a stranger. The decoder is the one place in the system where hostile bytes meet parsing code, so it is written defensively and fuzzed.

  1. Verify magic and spec_major before reading anything else.
  2. Validate index_offset and chunk_count against the actual file length before allocating.
  3. Cap total declared chunk length at the profile's cart budget. A 40-byte file claiming a 4 GB chunk must be rejected, not attempted.
  4. Walk chunks with bounds checks on every step. Never trust a length field twice.
  5. Refuse an unknown critical chunk (uppercase first byte); skip an unknown ancillary one silently.
  6. Return a typed error, never throw a raw exception into the player.

9.2 Cart id

cart_id = SHA-256(canonical bytes, excluding the sign chunk)
          -> first 160 bits -> Crockford base32 -> 32 chars
          displayed as 4 groups of 8
Decision — one hash function, not two

The specification's first draft said BLAKE3. Building it changed the answer: BLAKE3 in portable JavaScript is several hundred lines of tree hashing, kept bit-exact forever, for a marginal win on a 64 KB payload that SHA-256 hashes in about a millisecond. The runtime already carries a pure-JS SHA-256 with no platform branch, checked against the NIST vectors, and it is the same instrument behind every conformance chain. A second hash is a second thing that can disagree between implementations, and cart identity is the last place you want that.

Because the identity covers the label image and the recipe, the hash must be computed over the canonical serialization, not over whatever bytes happened to arrive: chunks in fixed order, four-byte alignment padding zeroed, no chunk appearing twice. The encoder produces canonical output; the decoder re-serializes canonically before hashing anything it did not write. Otherwise two byte-different files with identical content get different ids and reproducible builds mean nothing.

Gotcha — PNG steganography needs the alpha channel left alone

The .cart.png form stores payload in the low two bits of R, G, B and A across a 128 x 128 image — one byte per pixel, 16,384 bytes per image, so a full 64 KB cart needs a 256 x 256 label or a second image. Writing the low bits of alpha makes some pipelines premultiply and destroy the data. Use R, G, B only (six bits per pixel) and size the label accordingly, or keep alpha pinned at 255 and accept the smaller capacity. Decide this before the first cart ships, because it is baked into every published image.

10. The tokenizer

This was flagged as an open question in the specification. It is the first thing to close, because a budget that two tools disagree about is not a budget.

Rules, chosen to be simple enough that a second implementation matches on the first attempt:

  • Tokenize per the ECMAScript lexical grammar, InputElementDiv goal.
  • Every token counts as one. No exceptions, no free punctuation, no discounted keywords. Simple rules survive; clever ones drift.
  • Whitespace, line terminators and comments count as zero.
  • A template literal counts one per literal chunk plus one per ${ plus the tokens of each substitution.
  • A regular expression literal counts one.
  • Automatic semicolon insertion inserts nothing countable.

The implementation in core/tokenize.ts is normative. Fixtures live in conformance/tokens/ as source-and-count pairs, and a second implementation is conformant when it matches all of them. The counter is exposed in the editor and in sq1 build output, always, never behind a flag.

11. The stamper

Seven stages, seven pure functions. Each takes the previous stage's output and produces the next, with no shared mutable state — which is what makes the build reproducible and every stage independently testable.

resolve(recipe)            -> ResolvedRecipe   refs -> hashes -> bytes
merge(resolved)            -> MergedSpec       layer, later key wins
bind(merged)               -> BoundSpec        knobs -> values
validate(bound)            -> Diagnostic[]     empty = ok
compile(bound)             -> Payload          canonical byte order
pack(payload, assets)      -> CartFile         chunks, id, optional sign
prove(cart, replay)        -> HashChain        600 frames headless
Decision — diagnostics carry source positions

Every Diagnostic names the recipe file, line and column, the module that raised it, and what would satisfy it. This is the entire ergonomic case for the recipe format: an unbound knob or a tileset missing a ladder flag must read like a compiler error, not like a stack trace. If diagnostics are vague, authors will abandon recipes for the inline-code escape hatch and the module ecosystem never forms.

11.1 Reproducibility checklist

Same recipe, same module versions, byte-identical cart. Four things break this and all four are avoidable:

  • Map or object iteration order. Sort keys explicitly before serializing anything.
  • Timestamps. No build time, no file mtime, anywhere in the output.
  • Absolute paths. Store module references as hashes, never as paths.
  • Floating-point formatting. Knob values are parsed to 16.16 at bind time and serialized as integers. A recipe's 0.42 becomes 27524 in the cart, and never round-trips through a decimal string.

The CI check is one line: build twice in different directories, compare hashes.

11.2 The prover reuses the runtime

Because the worker is a pure function of its messages (section 3), the headless prover is the same runtime package driven from Node with a synthetic message loop. There is no second implementation of the machine, and therefore no second implementation to drift.

Decision — golden master exists before the first sprite is drawn

Build the frame-hash harness in milestone 1, when the machine draws nothing but a gradient. Determinism drift is silent, cumulative, and diagnosed by bisecting hash chains — which only works if the chains predate the drift. Every emulator project that added this late regrets exactly one thing.

What a conformance case looks like on disk

conformance/cases/spin-and-collide/

  replay.bin           4 bytes per frame, 600 frames

When a chain mismatches, the harness reports the first divergent frame number. That number, plus the reference PNG next to your actual output, is nearly always enough to find the bug in minutes.

13. Performance budget

16.67 ms per frame. The machine is small enough that the budget is embarrassing, which is the point — it should run at 60 fps on a five-year-old phone with the screen dimmed.

The allocation rule

Zero allocations inside tick(). Every buffer, entity pool and scratch array is created at load. No closures per frame, no array literals, no string concatenation, no boxed iterators. Garbage collection is the only thing in this design capable of causing a visible hitch, and the way to never think about it again is to never give it anything to collect.

Enforce it: in development builds, wrap tick() with a heap-delta probe and fail the performance suite if a reference cart allocates.

14. Milestones

Each has a binary acceptance test. "Looks right" is not one of them.

M0Core primitives

core/ only: fixed point, xoshiro128**, the sin table generator, the tokenizer. No console, no rendering, no cart.

Accept when the property suite passes 106 random pairs against BigInt for fmul and fdiv; the PRNG matches published xoshiro128** vectors; sin1024.bin is committed and byte-stable across two machines; the tokenizer matches every fixture.

M1Runtime skeleton and golden master

Worker, memory map, the message protocol, a hardcoded cart that draws a moving gradient. And the frame-hash harness.

Accept when a 60-frame run produces an identical SHA-256 chain on Node, Chrome and Firefox, on two different machines.

M2Container and CLI

cart/ plus sq1 build | validate | hash. Encode, decode, canonicalize, hash.

Accept when a cart round-trips byte-identically; sq1 hash agrees across machines; a cart with an unknown ancillary chunk loads and one with an unknown critical chunk is refused with a named error; 10,000 fuzz iterations produce no uncaught throw.

M3Real carts, scrubbed

The sandbox bootstrap, the ABI surface, faults and the watchdog. Hand-written JavaScript carts now run.

Accept when every canary cart fails to escape; a cart referencing Date or Math is rejected at build time with a line number; an infinite loop in tick() produces a fault and a recovered player within 200 ms.

M4Full rasterizer, audio, shell

Every gfx call, the four-channel synth, the touch shell, integer scaling.

Accept when a reference cart renders pixel-identical to ten committed PNGs; p99 tick() is under 4 ms on a mid-range phone; the allocation probe reports zero bytes per frame.

M5Stamper and the first engine

All seven stages, the module manifest format, one platformer engine, one art pack. Recipe in, playable cart out.

Accept when the same recipe built in two different directories on two machines produces identical cart ids; a recipe with an unbound knob fails with a file, line and suggested fix; the prover gates the pack step.

M6The second engine

A topdown engine, built against the module interface as it stands.

Accept when it ships with no changes to the provides/requires contract — or the required changes are documented as version 2 of the manifest format, with a migration for the first engine. This milestone is the honest test of section 8 of the specification, and failing it early is cheap.

15. The first week

M0 is small enough to finish in days and it de-risks the two things that cannot be fixed later.

  1. Scaffold the pnpm workspace and core/. No framework, no bundler yet.
  2. Write fmul, fdiv, sat, and the BigInt reference beside them.
  3. Write the property test. Run it for a million pairs. This is the moment the project either has a foundation or does not.
  4. Port xoshiro128** and check it against the published vectors.
  5. Generate and commit sin1024.bin, plus the generator and a test that regenerating it produces identical bytes.
  6. Write the tokenizer and twenty fixtures, including the awkward ones: template literals with nested substitutions, regex-versus-division ambiguity, ASI.
  7. Wire CI to run all of it on Node, Chrome and Firefox.

Then, and only then, decide whether the three amendments in section 1 are accepted — because by the end of that week you will have implemented the code that motivated all three, and the argument will be concrete rather than theoretical.
