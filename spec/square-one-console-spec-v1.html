0. How to read this

This specification is ordered by blast radius: what breaks if the decision changes later. That ordering is also the order in which the decisions must be made, because only the first tier is irreversible.

Why order by blast radius

Most console specifications rot because they interleave decisions that can never change with decisions that change weekly. Sorting by consequence produces the chapter order, the decision order, and the change policy from a single principle — and it makes Tier A small enough to argue about properly.

0.1 Normative language

MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. A requirement marked MUST is part of conformance (section 11); anything else is guidance.

1. Overview

Square One is a virtual console that runs in a browser. A game is a single file — a cart — that contains its code, art, audio, map data and, optionally, the recipe that built it.

The screen is square, 128 by 128 pixels. On a phone held in portrait, the square occupies the top and the console itself — bezel, cart title, player lights, pause, and a virtual d-pad and buttons — occupies the rest. The screen shape is what makes the device shape possible.

  PORTRAIT PHONE               LANDSCAPE / DESKTOP
  +---------------+            +-----------------------------+
  |     SHELL     |            |  SHELL     +-------------+  |
  |  +---------+  |            |  bezel     |             |  |
  |  | 128x128 |  |            |  title     |   128x128   |  |
  |  |  CART   |  |            |  P1 P2     |    CART     |  |
  |  +---------+  |            |  pause     |             |  |
  |               |            |            +-------------+  |
  |   (+)   A  B  |            +-----------------------------+
  |  dpad   X  Y  |
  +---------------+

Four properties define the system, and everything else in this document follows from them.

  • A cart is a pure function. Given a state and an input frame it produces the next state. It has no clock, no network, no host storage and no ambient authority of any kind.
  • Therefore replays are proofs. A recorded input log re-simulates to the identical result on any conformant implementation, forever. Rewind, save states, rollback netplay, regression tests and verifiable high scores are all the same feature.
  • A cart's identity is its content hash. A modified cart is a different cart with a different link. Authors sign; the signature is checkable by anyone.
  • Carts are built from a recipe, reproducibly. Rebuilding a recipe with the same module versions produces a byte-identical cart, so "this cart is what its recipe says" is a claim anyone can verify without trusting the publisher.

Tier A

2. The frozen core

Blast radius: every cart ever made, and every replay in the archive. Nothing in this section may change after spec 1 ships.

2.1 The cart contract

A cart MUST expose exactly two entry points:

boot(seed)   called once, after the cart image is loaded into RAM
tick()       called exactly once per simulated frame

A cart MUST NOT be given, and a conformant runtime MUST NOT expose: wall-clock time, network access, host filesystem or storage outside its own save region, the DOM, the ability to spawn execution contexts, or any source of entropy other than the console PRNG.

Why the contract is frozen but the language is not

Tier A fixes what a cart is — a deterministic state transition with no ambient authority. It deliberately does not fix what a cart is written in. That separation is what lets section 5.2 reserve a second payload type today and implement it in five years without invalidating a single existing cart.

2.2 Time

The simulation runs at exactly 60 Hz with a fixed timestep. tick() receives no delta. The only clock available to a cart is a u32 frame counter, readable at 0x20FC, which increments by one per tick and never by any other amount.

A runtime MUST decouple presentation from simulation using an accumulator, and MUST clamp catch-up to at most 5 simulation steps per presented frame.

Why 60 Hz fixed, and why an integer clock

Variable delta time is nondeterminism, and nondeterminism costs replays, rollback netplay, verifiable scores, regression tests and reproducible bug reports — all five, permanently. 60 rather than 30 because 30 Hz input sampling is felt immediately in any action game, and 16.67 ms is an enormous budget when the framebuffer is 8 KB.

The clock is an integer because an integer frame index is exact, serializable, and identical in 2026 and 2050. A cart that cannot see the wall clock cannot break on a leap day, cannot behave differently in another timezone, and cannot desync a replay.

The 5-step clamp exists because a backgrounded tab returning after 30 seconds would otherwise try to simulate 1,800 frames at once and enter a spiral it never leaves.

2.3 Numbers

The canonical numeric type is signed 16.16 fixed point held in an i32. 1.0 is 65536. Range is approximately -32768.0 to +32767.99998, with a resolution of 1/65536 of a pixel.

mul(a,b)  =  (i64(a) * i64(b)) >> 16      truncating toward zero
div(a,b)  =  (i64(a) << 16) / i64(b)      truncating toward zero
Intermediates MUST be 64-bit. Overflow saturates; it MUST NOT wrap.
Why fixed point rather than floats

IEEE floats are mostly deterministic, and "mostly" is worthless when a script interpreter is a valid runtime path. Fixed point is exactly reproducible on every implementation, faster on weak hardware, and makes "one pixel" the natural unit while keeping sub-pixel motion. The intermediate width and rounding mode are specified here because leaving either implicit is precisely how two conformant-looking implementations diverge on frame 4,000.

2.4 Randomness

The console owns exactly one PRNG: PCG32, with 64-bit state and 64-bit stream increment, multiplier 6364136223846793005, output function XSH-RR. Its 16-byte state lives at 0x2100 and is part of the machine snapshot.

rand32()   -> u32
rnd(n)     -> (u64(rand32()) * u64(n)) >> 32     unbiased, no division
rndf()     -> rand32() >> 16                     16.16 fixed in [0.0, 1.0)

There is no other entropy source in the machine. boot(seed) receives the session seed; the runtime MUST record that seed alongside any replay.

Why the algorithm is named, not described

"Use a good PRNG" is not a specification. Two implementations will choose differently, and every replay in the archive desyncs. The bounded form uses multiply-shift rather than modulo because modulo introduces bias that differs with n, and because it needs no division.

2.5 Input

The machine has four player slots, of which the Universal Profile populates two. Each slot is one byte, one bit per button:

bit 0  UP        bit 4  A     guaranteed reachable on touch
bit 1  DOWN      bit 5  B     guaranteed reachable on touch
bit 2  LEFT      bit 6  X     may be awkward on touch
bit 3  RIGHT     bit 7  Y     may be awkward on touch

Input is sampled once per tick, before tick() runs. Absent slots read as 0x00 and are reported absent in PLAYERS_PRESENT. Pause, menu and reset are console functions: they are not among the eight bits and a cart MUST NOT be able to observe or suppress them.

Why exactly eight buttons

Eight buttons is one bit each, which is one byte per player. A frame of input is four bytes; ten minutes of two-player input is 144 KB raw and roughly 2 to 5 KB after run-length encoding, because held buttons compress to nothing. That is what makes a replay small enough to attach to a bug report. Break the byte and the property is gone.

Eight is also the largest set that maps to every input device without invention: keyboard, any gamepad ever made, and — the binding constraint — touch, where a thumb-reachable d-pad plus two primary buttons is the honest maximum. The ninth button is always the one that breaks phones. The Game Boy shipped eight. The NES shipped eight. That is the thumb budget of two hands, not nostalgia.

Why four slots when only two are used

Four bytes instead of two costs nothing today and prevents a Tier A break the day someone wants four-player. Reserving address space early is free; reserving it late is impossible.

Why pause belongs to the console

One clause, and an entire class of hostile-cart behavior becomes impossible: no cart can trap a player in a game or forge the system menu. It also means the shell, not the cart, draws the touch controls — so every cart gets working touch input for free and no author ever thinks about it.

2.6 Machine state

The complete state of a running machine is 65,536 bytes of RAM plus the 16 bytes of PRNG state held inside it. There is no state anywhere else — no hidden registers, no host-side objects, no interpreter heap that outlives a snapshot.

Why one buffer, and why 64 KB

If the whole machine is one contiguous buffer, then snapshot, rewind and rollback are memcpy. Thirty seconds of rewind is 64 KB x 60 x 30 = 115 MB raw, which XOR-delta plus RLE reduces to roughly 3 to 6 MB. Affordable on a phone.

64 KB because every address is then a u16 and the entire memory map fits on one printed page. That legibility is the product: it is what lets a stranger implement this console in a weekend, which is what makes the format outlive its authors.

Tier B

3. The Universal Profile

Blast radius: every cart. Changing any of it means a new spec major, and the old core ships forever alongside the new one.

The Universal Profile (UP) is the normative machine. Every conformant player implements it in full, and every published cart contains a rendition that runs on it.

3.1 Display

Resolution128 x 128, square
Depth4 bits per pixel, 2 pixels per byte, low nibble is the left pixel
Framebuffer8,192 bytes at 0x0000, row-major
Live palette16 slots, each selecting one of 64 hardware colors
Refresh60 Hz, one tick() per presented frame
Why 16 colors

Four bits is half a byte, so two pixels pack into one. 128 x 128 at 4 bpp is exactly 8,192 bytes. Both numbers are powers of two because the packing works out — that is the engineering reason. 32 colors is a genuinely bad number: 5 bpp packs into nothing.

The design reason is stronger. A fixed 16-color palette forces every author to reuse the same colors, which is what makes a library of a thousand carts by a thousand strangers look like one console. No art direction can buy that.

Why square, and why 128

128 integer-scales to 512, 768 and 1024 with perfect pixels on any display. A 16 x 16 tile grid gives 8 x 8 tiles on screen, which is a readable density for pixel art. And square survives phone rotation, which 16:9 does not — more importantly, on a portrait phone the leftover rectangle is not waste, it is where the console goes.

3.2 Palette and remap

Three tables sit between a cart's color index and a screen pixel:

cart writes index i (0-15)
   -> DRAW_REMAP[i]     0x20D0, 16 bytes, identity at boot
   -> PALETTE_LIVE[..]  0x20C0, 16 bytes, each 0-63
   -> PALETTE_HW[..]    0x2000, 64 x RGB888
   -> screen

The reference hardware palette, which a cart MAY overwrite in full:

00 void0F orchid

Why a remap table rather than more bits

The remap layer is what stops 16 colors being a prison. Fades, damage flashes, day and night, and per-area color schemes all become a 16-byte write — no extra bits in the framebuffer, no extra fill cost, no change to any sprite. It is the cheapest expressive range in the whole machine.

Why the save region is 256 bytes and lives in the map

Putting persistence inside the address space means saving is poke, not an API with error states. 256 bytes is enough for progress, unlocks and a high score table, and small enough that a thousand carts on a phone cost a quarter of a megabyte. It is keyed by cart id, so one cart can never read another's save.

3.4 Audio

Four channels. Each selects one of five waveforms — pulse (with duty), triangle, sawtooth, noise, and a 32-step user wavetable — with per-channel volume, pitch and envelope. Music is pattern data driving the same four channels.

Why four channels

Melody, harmony, bass and percussion is the minimum complete arrangement; three forces you to drop one of them. The binding constraint is one nobody anticipates: the tracker has to fit on the console's own 128-pixel screen. Four columns fit. Eight do not. Letting the editor constrain the hardware is a healthy forcing function, not a compromise.

3.5 Budgets

Cart file65,536 bytes for the Universal Profile rendition
Code8,192 tokens as counted by the normative tokenizer
Sprites256
Map128 x 64 tiles
Save256 bytes per cart id
Why tokens and not bytes

A byte limit taxes comments, whitespace and descriptive names — it punishes readable code, which is exactly backwards when every cart ships its source and therefore every cart is also a tutorial. A token limit measures complexity, which is the thing worth bounding. Keep the counter permanently on screen and it becomes a game people enjoy losing.

The counter is normative and is defined by its reference implementation plus a fixture set, not by prose: tokenize per the ECMAScript lexical grammar, every token counts as one, whitespace and comments count as zero. No exceptions, no discounted keywords.

Why the counter is allowed to be imperfect

Deciding whether / begins a regular expression or is a division operator cannot be done correctly without a parser. The counter uses a one-token-lookback rule, which is wrong in three enumerated cases, each pinned by a fixture recording both this count and the count a real parser would give.

That is deliberate. The failure mode is a slightly wrong count, never a wrong program — the engine still parses the cart correctly. And a rule that never looks past one previous token is one a second implementation can reproduce exactly on the first attempt, which is the entire reason to have a normative counter at all. A perfect rule that nobody re-implements correctly would be worth less.

3.6 The shell

The shell is everything outside the 128 x 128 window: bezel, cart title, player indicators, pause, and the virtual controller on touch devices. It is drawn by the console. A cart MUST NOT be able to write a single pixel outside its framebuffer, render text into the shell, or influence its appearance.

Shells are skinnable and ship as Tier F modules, the same as sprite sets.

Why the shell is a security boundary, not decoration

Because the shell is always console-drawn and always present, a cart can draw a convincing fake login box inside its window and it will still be visibly inside a game screen, inside a console, with no address bar and nowhere to submit. Chrome that the untrusted content cannot reach or imitate is the same mechanism a browser uses for its own URL bar.

Why the console supplies its own sine and cosine

Math.sin, cos, exp and pow are not specified to bit precision in ECMAScript. V8 and SpiderMonkey genuinely differ in the last unit in the last place. That difference is invisible in an ordinary application and it will desync a replay between Chrome and Firefox. So the console ships a fixed-point table, and the host's math library is removed entirely (5.2).

Tier D

5. The cart container

Blast radius: tooling. Forward-compatible by design, so new chunk types never break old players.

5.1 Three forms of one thing

.cartThe binary container. What a player loads.
.cart.pngThe same bytes carried in the low two bits of a 128 x 128 label image. The cart is a screenshot you can post anywhere, and drag back in to play.
recipe.tomlThe source. Small, readable, diffable in git. Section 8.

5.2 Header and payload type

offset  size  field
 0      4     magic         "SQ1C"
 4      2     spec_major    u16 LE
 6      2     spec_minor    u16 LE
 8      4     chunk_count   u32 LE
12      4     index_offset  u32 LE  -> chunk directory

The payload type is declared in META:

script/js1Ships now. JavaScript source text, executed in a Worker inside a scrubbed realm. Source is mandatory and always visible.
wasm/1Reserved. Defined here, implemented later or never. A wasm/1 cart without an accompanying source chunk is displayed with a visible unverifiable badge.

The scrubbed realm

For script/js1, the runtime MUST delete from the cart's global scope, at minimum: fetch, XMLHttpRequest, WebSocket, importScripts, Worker, SharedArrayBuffer, crypto, Date, performance, Intl, eval, Function, WeakRef, FinalizationRegistry and Math. All intrinsic prototypes MUST be frozen. The Worker MUST be terminated if a single tick() exceeds the frame deadline by a configurable margin.

Why JavaScript source is the payload that ships

Easy for anyone. No toolchain, no compile step, no new language. Type in a box and press run. And an AI writing carts is more reliable in JavaScript than in anything else by a wide margin, which matters a great deal for section 9.

Lightweight, counterintuitively. You ship no interpreter at all — V8 and SpiderMonkey are already in the browser and already JIT-compiled. A hand-written bytecode VM would be elegant and roughly 5 to 20 times slower per operation, and you would own its performance forever.

Verifiable in the way that matters. A hash over a binary proves identity, not safety: it says "this is the cart three thousand people played", and cannot say what the cart does. Source text gives you both — hash it and read it, with meaningful diffs between versions. Every cart is simultaneously a game, a tutorial and its own audit trail.

The honest cost. You cannot hard-meter CPU in a Worker; you get a watchdog and a kill, not an instruction budget. And isolation is realm scrubbing rather than memory separation. Both are acceptable when the box around the cart has no network and no cookies — and if hard metering is ever needed, wasm/1 is already reserved.

5.3 Chunks

Each chunk is a 4-character type, a u32 LE length, the payload, and zero padding to a 4-byte boundary. An uppercase first character means critical; lowercase means ancillary. A player MUST refuse a cart containing an unknown critical chunk, and MUST skip an unknown ancillary chunk without complaint.

Why steal PNG's case convention

The uppercase/lowercase rule is one sentence of specification that buys a decade of forward compatibility: a 2026 player can safely open a 2032 cart, ignoring the parts it was never told about, and refuse exactly the carts it genuinely cannot run. PNG has survived on that convention since 1996.

5.4 Identity and signing

cart_id = SHA-256( every byte of the canonical encoding except the sign chunk )
          truncated to 160 bits, Crockford base32
          displayed as 4 groups of 8:   K3PQ7W2M-N0XR8T4V-...

The identity covers the label image and the recipe, and excludes only the signature. Signing is optional; an unsigned cart is valid but shows as unattributed.

Why SHA-256 and not BLAKE3

Draft 1 of this document specified BLAKE3. Implementation review changed it. BLAKE3 in portable JavaScript is several hundred lines of tree hashing — a second hash function to get bit-exact and keep that way forever — bought for a marginal speed win on 64 KB, where SHA-256 costs about a millisecond.

SHA-256 is already in the runtime as a pure 32-bit implementation with no platform branch, verified against the NIST vectors, and it is the same instrument that produces the conformance frame-hash chains. One hash function in the system beats two. A second one is a second thing that can disagree between implementations, and cart identity is exactly where disagreement is unaffordable.

Why the label is inside the hash

The tempting design excludes ancillary chunks so a cart can be re-labelled without changing identity. That is a scam vector: swap the screenshot on a well-known cart and you have a different game wearing its face at the same address. Only the signature is excluded, because it cannot cover itself.

5.6 Where a cart's static data lands

Section 3.3 says a cart's static data initializes 0x2000 through 0x77FF at boot. These are the chunks that do it, and the regions they fill:

ChunkAddressBytesRegion
PAL 2000224PALETTE_HW, PALETTE_LIVE, DRAW_REMAP
GFX 4200 then 22008,448SPRITE_FLAGS then SPRITES
MAP 43008,192MAP
SFX 63003,328SFX
MUS 70002,048MUSIC
DATA780034,560USER_RAM

Installation happens after RAM is zeroed and after the boot defaults are written, and before the cart's own boot() runs. Both halves are load-bearing: install before the defaults and the identity live palette overwrites the cart's own colours; install after boot() and a cart cannot read its own tiles on the frame it starts on.

A chunk shorter than its region fills from the start and leaves the rest as boot left it. A chunk longer than its region MUST be refused as a load error and MUST NOT be truncated. Nothing maps to 0x20E0..0x21FF and nothing may — CLIP, CAMERA, the input bytes, FRAME, RNG_STATE and the audio registers live there, and a chunk reaching them could overwrite the seed the machine was booted with, making a cart's replay a function of its own data file.

Why GFX  carries its flags first

Sprites and their flags are adjacent in RAM, and a sheet without its flags is half a tileset, so one chunk carries both — but not in address order. A flat image of 0x2200..0x42FF would have to be at least 8,193 bytes long before it could say anything at all about a flag, because the flags begin at offset 8,192.

Measured on a real cart using 96 of the 256 cells, that is 3,072 bytes of pixels, then 5,120 bytes of zeroes, then the flags — which cancels the entire saving this arrangement exists to make. Putting the fixed-size half first lets the split be a constant rather than a header, and leaves the variable-length half at the end where trailing zeroes trim away.

Why the palette is critical rather than ancillary

A cart whose live slots index a hardware palette it did not choose looks different on a player that ships a different reference table. Marking PAL  critical means such a cart is refused by a player that does not understand it rather than silently rendered in the wrong colours — which is exactly the distinction the uppercase/lowercase rule exists to draw.

5.7 Renditions

A cart MAY carry additional renditions for extended profiles in rndr. The chunk directory sits in the header, so a lightweight player MAY issue an HTTP range request for the Universal Profile chunks alone and never download the rest. Rich carts stay rich; cheap players stay cheap.

Cross-cutting

6. Profiles and the downlevel rule

The single rule that keeps the library coherent:

Every published cart MUST contain a valid Universal Profile rendition. Extensions may enhance. They may never gate.

A cart declares its relationship to extensions the way glTF does, and the distinction is load-bearing:

uses     = ["pointer", "hires-256", "audio-8ch"]   soft: use it if present
requires = []                                      hard: refuse to run without
Why the fallback is mandatory rather than encouraged

Every platform that let extensions ship without a required fallback fragmented — early WebGL extensions, OpenGL ES, Android feature flags. Every platform that enforced one stayed coherent. The rule only works if a machine enforces it, which is why section 9's stamper refuses to pack a cart whose Universal rendition fails the prover.

6.1 How stamping down works

MechanismHandlesAuthor effort
Automatic asset downlevel64 colors to 16 with a specified dither; 256 x 256 art to 128 x 128; 8-channel mixdown to 4; a 12-button scheme onto 8 via a declared mapping tableNone — deterministic processing in the stamper
Declared degradationA [downlevel] block naming features to drop and knob values to substituteAbout ten lines
Separate Universal recipeCases where the rich version is genuinely a different gameFull, always available
Why input cannot be downleveled, and the rule that follows

Automatic downlevel works on assets and never on mechanics. There is no transformation that turns "requires a mouse" into buttons. So: an extension may add fidelity and convenience; it may not add a mechanic required to finish the game. A pointer may make aiming nicer, and the game must still be completable on eight buttons. That is checkable rather than aspirational — the prover runs the Universal rendition to completion against a button-only replay.

Tier E

7. Engines

Blast radius: carts that opt in. Free to evolve, because a cart pins a version and the engine is just payload inside it.

An engine is a behavior template: an entity model, an update loop, and a declared set of knobs. Engines are not part of the machine. They ship as modules, they are compiled into the cart, and a cart from 2026 keeps the engine it was built with forever.

Planned first set: platformer, topdown, shmup, puzzle-grid. The second one is the one that matters — see section 13.

Why engines live outside the spec

This is the whole reason for the tier ordering. Engines and art are where all the volume and all the fun are, and putting them inside the machine would make every one of them a compatibility liability. Outside it, they are data: versionable, forkable, replaceable, and free.

Tier F

8. Modules and recipes

Blast radius: nothing. This is where the ecosystem lives.

8.1 Modules

Everything loadable is a module: content-addressed, versioned, and carrying a manifest that declares what it provides and what it requires.

Why modules declare an interface, not just data

This is the decision the whole stamping system turns on. Because an engine states what it needs and a tileset states what it offers, a recipe can be type-checked before anything is built. That is the difference between a template system that stamps working carts and one that stamps plausible-looking broken ones.

8.2 The recipe

The recipe is the source; the cart is the build artifact. Recipes go in git. Carts go in the registry.

[cart]
title   = "Cave Runner"
author  = "eric"
profile = "up"
spec    = 1

[engine]
use = "platformer@2.1"          # blake3:9f3a1c...

[modules]
palette   = "sweetie16@1"
tileset   = "caves-8x8@3"
spriteset = "hero-4dir@1"
soundbank = "chip-basic@1"
content   = "./world1.map"

[tuning]
gravity        = 0.42
jump_velocity  = -3.10
coyote_frames  = 6
run_accel      = 0.35
max_run        = 2.00

Layers merge in declared order and later keys win, exactly as CSS and container images do: engine → genre pack → art pack → tuning → cart overrides. A recipe MAY carry inline custom code, which counts against the same token budget as everything else.

Why layers, and why the escape hatch is taxed

Layers are content-addressed and shared, so a hundred carts using one tileset store it once and ship only their diffs. And the escape hatch has to exist — without it the system is a toy that can only make games it already knows — but taxing it keeps it the exception rather than the path of least resistance.

Tier G

9. The stamper

Blast radius: nothing. But this is the machine that makes the rest usable.

The stamper is not a code generator. It is a resolver and a merger — a far more reliable class of program, and one whose failures are validation errors with line numbers rather than crashes three minutes into a playtest.

  recipe.toml
      |
  [1] RESOLVE    name@version -> content hash -> module bytes
      |
  [2] MERGE      layer in declared order; later key wins
      |
  [3] BIND       knobs -> values; an unbound required knob is an error
      |
  [4] VALIDATE   interfaces, budgets, ABI minor, profile rules
      |
  [5] COMPILE    engine + content -> payload, canonical byte order
      |
  [6] PACK       chunks -> .cart; hash -> cart_id; optional sign
      |
  [7] PROVE      headless run, 600 frames, replay input,
      |          frame-hash chain must match
      v
  game.cart      immutable, content-addressed, playable

9.1 Reproducible builds

The same recipe with the same module versions MUST produce a byte-identical cart. This is what makes the content hash meaningful, makes caching free (immutable, max-age=31536000), and turns "this cart is what its recipe claims" into a fact anyone can check without trusting the publisher or the registry.

9.2 The prover

A cart is not packed until it has been run headless for at least 600 frames against a replay, with the SHA-256 chain of per-frame framebuffer hashes recorded into rcpe. For a cart declaring extended profiles, the Universal rendition is the one that must pass.

9.3 Where the AI sits

  SPEC.md  --[ AI ]-->  recipe.toml  --[ stamper ]-->  cart  --[ prover ]-->  pass/fail
                             ^                                                    |
                             +------- knob edits from the play overlay -----------+
Why the AI writes recipes and not code

Forty lines of validated data instead of two thousand lines of hopeful JavaScript. The nondeterministic step produces something small and checkable; the deterministic step is actually deterministic. Iteration becomes a knob tweak and a sub-second rebuild rather than a code edit and a page reload — which is the same finding as "sliders beat asking the model to recode values", generalized into an architecture.

9.4 Module promotion

Inline in one cart → extracted to a local module → published with a version. The trigger is the second use, never the first.

10. Security model

Almost all of this falls out of decisions made for other reasons. Where a threat is stopped by architecture rather than by policing, it stays stopped without anyone being paid to watch.

ThreatWhat stops it
Someone edits a popular cart and reuploads itContent-addressed identity. A modified cart is a different cart at a different address
Impersonating an authorsign chunk, ed25519. Verifies against the author key or shows unattributed
Cart exfiltrates data, mines, or phones homeStructurally impossible. There is no network in the sandbox — not policed, absent
Cart draws a fake login or payment screenCannot draw outside 128 x 128, cannot open a URL, has nowhere to submit. It can draw a lie and cannot deliver it
Poisoned module reaches a thousand cartsHash-pinned recipe plus reproducible builds. Anyone can rebuild and compare the cart id
Faked high scoresReplays are proofs. Re-simulate a 3 KB input log server-side
Cart hangs the deviceWorker watchdog and terminate

10.1 Containment layers

A conformant player MUST run cart code on a separate origin, in an iframe with sandbox="allow-scripts" and without allow-same-origin, under a Content Security Policy including connect-src 'none', inside a Worker it can terminate. A cart that escapes the realm scrub still lands in a box with no network and no cookies.

10.2 What a host must not do with a cart's own words

Three strings originate with the cart author and travel outward into the host's interface. Each is a channel, and each has a rule.

StringRule
The META titleRendered as text, never markup. Capped at 64 UTF-8 bytes and free of control characters at the container level, so the cap is enforced before a host sees it. It MUST NOT be placed where a system message appears.
A load or validation error messageError messages name the chunk and quote the title, so a rejected cart's own text ends up inside a diagnostic. A host MUST NOT render one as HTML. This is the least obvious of the three, because the string reads like the host's own words and is not.
Anything drawn to the screenConfined to the 128 x 128 framebuffer by construction; no rule needed beyond section 3.6.
Why an error message is a cart-controlled string

Found while building the reference player, in the reference player. A hostile cart cannot reach the DOM — but it can choose its own title, get itself rejected on purpose, and have the host paste the resulting sentence into the page. If that sentence is written with innerHTML the cart has markup injection into the shell, from a code path whose entire purpose was refusing it.

The general shape is worth remembering: a diagnostic about untrusted input is itself untrusted output. Sanitising the input and then interpolating it into an error you trust puts the taint straight back.

10.3 In-process execution is not a deployment mode

Realm hardening cannot run on a realm shared with the page: deleting Function or freezing intrinsics would break the host around it. So a player that runs a cart on the main thread has Layer 1 only, and the escapes recorded in the canary suite are open.

That configuration is legitimate for tests and for authoring tools, and it MUST NOT be the default for a player that loads carts a person did not write. A conformant player MUST default to a real Worker with the realm scrubbed, and any in-process path MUST be opt-in and named as such.

11. Conformance

An implementation may call itself Square One 1 conformant if and only if:

  1. It passes the golden-master suite: for every published test cart and replay, the SHA-256 chain of per-frame framebuffer hashes matches the published chain exactly.
  2. It implements the full Tier C ABI at the minor it declares.
  3. It refuses carts with unknown critical chunks and accepts carts with unknown ancillary chunks.
  4. It never exposes wall-clock time, network, or host storage to a cart.
  5. It draws the shell outside the 128 x 128 window and never lets a cart write there.
Normative — must match bit for bitImplementation-defined
Framebuffer contents at the end of every tick; PRNG sequence; fixed-point arithmetic and rounding; input sampling order; chunk parsing and rejection; cart id derivation Upscaling filter and any CRT treatment; audio mixing quality beyond the specified waveforms; shell appearance; editor behavior; frame presentation timing
Why audio is not normative

Audio does not feed back into simulation state — the sim emits commands and the mixer consumes them, one way only. So mixing quality can differ between a phone and a desktop without any replay diverging. Building that one-way street is also why the audio clock must never drive game timing.

12. Open questions

  • System font. Is the 4 x 6 font in ROM, and does a cart's custom font count against the sprite budget or the cart budget?
  • Save region across renditions. One save keyed by cart id, shared by every rendition — or one per rendition? Sharing is friendlier and risks a rich rendition writing a layout the Universal one cannot read.
  • Waveform definitions. The five waveforms need exact sample-level definitions if anyone ever wants audio to be normative.
  • Whether wasm/1 is ever implemented. Reserving it costs a paragraph. Building it is a project.
  • The name. Square One is a working title.
