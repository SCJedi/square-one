# Conformance

Normative test data. These bytes define what Square One *is*; an implementation is conformant
when it reproduces them exactly. Nothing here is regenerated casually — CI fails if
regeneration changes a single byte.

## `fixtures/`

| File | What it pins |
|---|---|
| `sin1024.bin` | 1024 entries of 16.16 sine, 4096 bytes. Generated by `packages/core/tools/gen-sin.ts` in exact BigInt arithmetic, never by `Math.sin`. |

## `tokens/`

Source-and-count pairs defining the 8192-token cart budget. `expected.json` maps each fixture
filename to its token count. Every count was derived by hand before the tokenizer ever ran on
it — deriving expectations by running the implementation you are testing makes the test
tautological, which is the easiest way for a conformance suite to be worthless.

## `cases/`

Golden-master runs. Each case is a directory:

```
cases/<name>/
  seed.txt      the session seed the run was booted with
  replay.bin    4 bytes per frame - one input byte per player slot
  chain.txt     one SHA-256 frame hash per line, plus the final chain digest
```

The chain is defined in `packages/runtime/src/hash.ts`:

```
frameHash_i = sha256( framebuffer bytes 0x0000..0x1FFF at the end of tick i )
chain_0     = sha256( ZERO32 || frameHash_0 )
chain_i     = sha256( chain_{i-1} || frameHash_i )
```

Per-frame hashes exist so a mismatch reports the **first divergent frame**, which is what makes
a desync debuggable. The chain exists so a whole run compares as one value.

## Adding a case

1. Write or pick a cart and an input replay.
2. Run `npm run gen:golden` to produce the case directory.
3. **Look at the rendered frames before trusting the hashes.** A golden master locks in
   whatever the code did on the day you generated it, including a bug. Generating a case is
   an assertion that the output is correct, not merely that it is stable.
4. Commit the case. From then on, any change to its bytes is a deliberate act that has to be
   explained in the commit message.
